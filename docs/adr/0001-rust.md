# ADR 0001 — Write the control plane in Rust, keep the world servers in C

- **Status:** Accepted. Extended to the whole stack, with the AzerothCore translation map, in
  `docs/adr/0007-rust-translation.md`.
- **Date:** 2026-10-25
- **Context:** the auth service is the control plane: an auth endpoint, a session store, a directory and an
  allocator. It is small, long-running, network-facing, and concurrent by nature — one listener,
  many world connections, many client connections, all state machines over sockets. The world
  servers, which are large and computationally heavy (map data, agents, pathfinding), already exist
  in C and are not part of this repository.

## Decision

Write the control plane in Rust — the auth service first, since it is the only program in
phase 1 that has to be new. Keep the world servers in C. The two talk over the world-link protocol
(`docs/03-protocol.md`), which is a small, fixed-layout message set over TCP.

## Why Rust for this half

- The work is exactly what the language is good at: sockets, state machines, owned message buffers,
  no garbage collector pausing a latency-sensitive handshake.
- `#[repr(C, packed)]` structs plus a byte-cursor encoder give exact, readable control over wire
  layouts — the same control C gives, with bounds checks on the parsing side, where the client's
  input is hostile by assumption.
- Concurrency without the class of bug that would be worst here: a shared directory mutated by
  every world's heartbeat is precisely the shape that produces heisenbugs in C.
- Tooling that this project needs: `cargo test` for protocol round-trips, easy static assertion of
  struct sizes, a dependency story that is not "vendor a build system first".

## Why not Rust for the world servers

- They contain the accumulated work of the whole GWPS project — map import, paths, items, agents —
  and they are correct enough to be the reference for the client protocol. Rewriting that is a
  separate, much larger project with no shared benefit.
- The interface between the halves is small and stable, so the cost of the split is bounded.

## Cost, stated plainly

The one thing the auth service must reproduce bit-for-bit is the client handshake: DH with the fixed prime and
server private, ARC4 framing, and the exact redirect layout. In GWPS that is working C. In Rust it
is a port that has to be re-proven, and when it is wrong the client says `007` and nothing else.

Mitigations, all of which are in the roadmap:

- the C reference stays runnable and is the oracle (`docs/04-from-gwps.md`);
- packet traces exist and a diff tool exists (`PreSearing/tools/diff-transitions.py`);
- the handshake is milestone M3, isolated, with login as its single acceptance test;
- crates for the primitives (`arc4`, big-integer modexp) exist, so it is engineering, not research.

## Alternatives rejected

- **C, evolving GWPS in place.** Lower porting risk, but inherits the process model that caused the
  scaling problem, and gives up every safety and tooling advantage where concurrency is heaviest.
- **C, new structure.** Same as above but with a rewrite cost *plus* the porting risk; strictly
  worse than Rust.
- **Go or C#.** Both are viable and would work; Rust was chosen for the absence of a runtime and
  for exact-layout control without a GC in the connection path.

## Consequences

- Two languages in the project. Accepted: the boundary is a small protocol, not a shared ABI.
- The world-link protocol must be explicitly versioned and validated, because a mismatch now
  crosses a language boundary.
- Rust knowledge is required to work on the auth service. Mitigated by keeping the crate layout small and the
  message definitions declarative.
