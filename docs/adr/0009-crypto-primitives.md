# ADR 0009 — Crypto primitives: a hand-written ARC4, and a big-integer crate for the exponentiation

- **Status:** Accepted
- **Date:** 2026-10-25
- **Relationship to the rule:** `docs/adr/0006-azerothcore-is-the-reference.md` asks that a deviation be
  recorded before it is implemented, and `docs/adr/0007-rust-translation.md` that a dependency arrive
  with the code that needs it, with its reason written down. This ADR is both records.

## Decision

1. **ARC4 is written here, faithfully, not imported.** Twenty lines of key schedule and byte generator,
   ported from GWPS `arc4.c`.
2. **Modular exponentiation comes from a crate** (`num-bigint-dig`), isolated behind one function,
   `asura_protocol::client::handshake::modpow`.
3. **The key derivation (`arc4_hash`) is written here**, ported from GWPS `AuthSrv.c`, and pinned
   byte-for-byte against fixtures generated by compiling the reference's own C.
4. **One deviation from the reference's behaviour**, recorded below: a degenerate (zero) shared secret
   is refused instead of used.

## Why ARC4 is not a dependency

The requirement is not "a secure stream cipher". It is "the same 256-byte permutation and two counters
that the client will run", against a fixed key, forever. RC4 is cryptographically broken and no
maintained crate should be trusted to still be shipping it; the crates that do are either
unmaintained or a thin wrapper around the same twenty lines. Importing one would add a supply-chain
surface and an MSRV constraint to buy nothing — while the property that actually matters, byte-exactness,
would still need the same tests.

So the code is here, and the tests are the guarantee:

- published RC4 known-answer vectors (`Key`/`Plaintext`, `Wiki`/`pedia`) prove it is *standard* RC4;
- keystreams generated by compiling the reference's own `arc4.c` prove it is *the same* RC4
  (`tools/gen-handshake-fixtures.py`, `handshake_fixtures.rs`).

If RC4 were ever replaced by something the client also speaks, this ADR is void and a new one is
written.

## Why the exponentiation is a dependency

The exchange is `shared = client_public ^ server_private mod prime`, with a **fixed** 512-bit prime and
a **fixed** 511-bit exponent (`main.c`). What is needed is square-and-multiply over 512-bit numbers:
a 1024-bit product, then a reduction modulo a 512-bit modulus. Hand-writing that means limb arithmetic
and a Montgomery (or Barrett) reduction — roughly a hundred lines where a carry bug produces a wrong
secret, a keystream the client cannot reproduce, and an error message that says only `007`.

The judgement: this is the one place where a mistake is expensive *and* hard to localise, and where a
well-worn implementation exists. `num-bigint-dig` is the RustCrypto fork of `num-bigint` — the crate the
`rsa` crate uses for the same operation — and it is isolated behind `modpow`, so replacing it is a
change to one function.

Two consequences accepted deliberately:

- **Not constant-time.** Irrelevant here and worth stating: the exponent and modulus are public
  protocol constants, so there is no secret for a timing side channel to leak. If anything in this
  project ever needs real key agreement, it does not get to use this module.
- **One more dependency.** `default-features = false, features = ["u64_digit"]`: the `std` feature
  would drag in `rand` and `serde` for two features we do not use.

## Why the key derivation is hand-written

`arc4_hash` is not a standard construction, so no crate implements it: it borrows SHA-1's initial values
and two of its round constants, runs five rounds over 20 bytes, and *adds* the working state back onto
the input words. It must be reproduced exactly, and "exactly" is not something careful reading
establishes — which is why the fixtures exist. Writing it also revealed the shape of the risk: the first
version had one wrong hex digit in a round constant (`0x6ED9_9BA1` for `0x6ED9EBA1`), which changed
three bytes of the digest and was caught by the fixture comparison, not by review.

## The deviation: a zero shared secret is refused

If the client's public value is zero (or congruent to zero modulo the prime), the shared secret is zero,
the master secret is its own seed, and the connection is scrambled with a key that was never exchanged.
GWPS computes it and carries on. ASURA returns `HandshakeError::DegenerateSecret` and drops the
connection.

Why this is safe to add: the patched client's public value comes from its own key material, so a real
client cannot present a congruent-to-zero value; and a refusal here is a dropped connection, not a
different protocol. Why it is worth adding: the alternative is a login path that will happily scramble a
session with a key it did not agree, and nothing downstream would notice.

## What the fixtures are, and what they are not

`tools/gen-handshake-fixtures.py` compiles a C program out of the reference's own text — `arc4.c`
verbatim, and `arc4_hash` extracted verbatim from `AuthSrv.c` — and writes its output into
`handshake_fixtures.rs`. The exponentiation rows come from CPython's `pow()`, a different implementation
in a different language.

They pin the arithmetic and the message formats. They do **not** prove the client will accept the
handshake: only the real client can settle that, and M3's acceptance criterion is still the packet
trace diff against GWPS (`docs/roadmap.md`). The fixtures exist so that when the client is pointed at
this, the difference — if there is one — is not arithmetic.

## What would change this decision

- A measured need for constant-time arithmetic (a real key agreement, i.e. not this protocol).
- A port of the key exchange to a different cipher the client supports.
- `num-bigint-dig` becoming unmaintained: swap it behind `modpow` for upstream `num-bigint` and note it
  here.
