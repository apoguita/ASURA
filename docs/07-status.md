# Status: what works, what is a stub

Generated by `tools/parity-report.py --write docs/07-status.md`. Do not edit by hand: a status
table typed by hand is a status table that is wrong in a month.

It compares this repository with the GWPS reference's own dispatch switches, so *missing* means
"the reference acts on this message and we do not".

## Implemented handlers

28 of the reference's client-message handlers are present in this repository.

## No-ops in the reference itself

The reference's handler ignores every parameter and does nothing a client can observe.
Implementing these would be inventing behaviour, so they are a deliberate gap rather than
missing work:

- `GAME_CMSG_ITEM_UPDATE_EQUIPPED_COLOR` (`0x8084`) -- GameSrv_HandleChangeEquippedItemColor ignores all three parameters (UNREFERENCED_PARAMETER) and returns ERR_OK

## Missing, with real behaviour in the reference

- `GAME_CMSG_CHAR_CREATION_REQUEST_PLAYER` (`0x8089`)
- `GAME_CMSG_CHAR_CREATION_REQUEST_ARMORS` (`0x808A`)
- `GAME_CMSG_CHAR_CREATION_CHANGE_PROF` (`0x8060`)
- `GAME_CMSG_CHAR_CREATION_CONFIRM` (`0x808B`)

## Known partial areas

Handlers are the floor, not the whole of parity. These are implemented *and* limited, stated so
that nobody reads the table above as more than it says:

- **movement** has no pathfinding: `MOVE_TO_COORD` answers with the client's own destination
  rather than the next waypoint of a path, so a straight line can cut a corner
  (`crates/asura-world/src/agent.rs`);
- **world state** is one agent: no NPCs, no other players, no combat, no quests;
- **items** are rows (`asura_db::inventory`), and the block sent for them is the reference's own
  down to the byte (`crates/asura-world/src/lib.rs`, the byte-equality test against the capture).
  What works: dropping (with the stack actually deducted, which the reference never does), moving
  an item between slots, and wearing one. What does not: buying, selling, salvaging, identifying,
  splitting a stack by hand (a drop splits; nothing else does), and **picking anything up** -- the
  reference has no pick-up handler and this one has none either, so a dropped item is litter for
  the rest of the session. `DROP_ITEM` is the one item message the reference's dispatch acts on;
  its handler is unfinished there (a `TODO` for partial stacks, no removal) and this port finishes
  it -- a recorded deviation, argued in `docs/08-next-inventory-model.md`. What a drop *sends* is
  **nothing**, and that is not configurable: `ITEM_REMOVE` (`0x014D`) and an item agent (`0x0020`
  with `AgentType_Item`) are both in no capture and a live client crashed on each of them. Dropping
  still deducts, and the client does its own subtraction -- measured. A move is answered with
  `ITEM_MOVE_TO_LOCATION` (`0x013E`), which is in the capture. `ITEM_MOVE` and `EQUIP_ITEM` are
  messages the reference does not dispatch at all, so their behaviour here is this project's;
  `UNEQUIP_ITEM` (`0x804F`) is not implemented because its layout carries no item id and no
  capture has shown what it means (dragging an item out of the equipped bag arrives as
  `ITEM_MOVE` and works);
- **instances** are prebuilt per map and never created on demand, and only outposts are hosted;
- **persistence** saves where a character stood when it leaves and puts it back there when it
  returns (`asura_db::game::record_position`). That is a thing the reference does *not* do -- it
  keeps a character's last map and re-spawns at the map's own spawn point every session -- so a
  character's position is a deliberate addition, recorded in `0006_inventory.sql`. The inventory is
  durable too, because it is rows: a drop, a move and an equip all survive a relog. Nothing else
  about a character is saved yet: no level, no profession, no gold, no quest state;
- **character creation** (the four `CHAR_CREATION_*` handlers) needs two things this server does
  not have. The reference only offers it inside a *character-creation* instance (its
  `MapType_CharacterCreation`), and this world hosts outposts only; and
  `GameSrv_HandleCharCreationChangeProf` answers with the default equipment for the chosen
  campaign and profession (`GetDefaultEquipments`), a table this project has not ported. Doing
  the handlers without those two would send a creation screen the client cannot leave with a
  character it cannot equip;
- **the game connection's front door** is a byte-copy router; the reference hands the socket
  itself to the game server, which needs one process and is not what this does
  (`crates/asura-auth/src/frontdoor.rs`).

## Chat and chat commands, command by command

`GAME_CMSG_SEND_CHAT_MESSAGE` counts as *implemented* above because this repository has code for it,
which is a lower bar than this table uses. What the two servers actually do with a typed line, read
out of `GmChat.c` and `GmCommands.c`:

| typed | the reference | here |
|---|---|---|
| `!text` | `Channel_All`, sent | `Channel_All`, sent, and printed here |
| `#text` | `Channel_Group`, sent | `Channel_Group`, sent, and printed here |
| `$text` | `Channel_Trade`, sent | `Channel_Trade`, sent, and printed here |
| `@`, `%`, `"` | ignored | ignored |
| `/stuck` | cancels the movement and broadcasts the agent's position (`0x002C`) | the same, and printed here |
| `/maps` | lists its configured maps **in its own log** | lists the maps this world hosts, in this log **and** on the wire |
| `/tp <map>`, `/teleport <map>` | asks the auth service for a world and tells the client to reconnect | **not implemented**: this world cannot start a travel |
| anything else after `/` | `Unknown command`, in its log and on the wire | the same, here and on the wire |

**Nothing is gated, and nothing must be.** No chat text has ever reached a client's screen in this
project or in the reference -- the reference's `/maps` was useful because it printed its answer on
the *server*, and so does this one -- so a switch that hid the answer would hide the only half that
has ever worked. Both servers send these messages anyway; whether a client renders them is the open
question, and none of the three chat messages appears in any capture. The one command that acts
there and not here is `/tp`, which needs world-initiated travel: a slot reserved, a transfer row
written, and `GAME_SMSG_TRANSFER_GAME_SERVER_INFO` sent -- a message that, like the three that have
crashed a client, is in no capture yet.

## Features the reference has but keeps switched off

Parity with GWPS includes matching what it *disables*, not only what it implements. From its own
source:

- **chat sending** is gated in the reference (`GameSrv_ChatSendingEnabled`, `GWPS_CHAT=1`) and is
  *not* gated here. Its comment records that an unconditional send put a message on the wire the
  client could not parse, **and that it crashed the client**; this port tried the same thing and a
  live client crashed on `!hello` too. What the gate is for differs, though: the reference used it
  to protect its client, and this project concluded that hiding the answer serves nobody -- so both
  halves happen (the answer is printed here, which always worked, and it is sent), and nothing sits
  behind a variable. None of the three chat messages appears in any capture, which is why
  *rendering* is unproven rather than why sending is switched off;
- **GM commands**: the reference has `/tp`, `/teleport` and `/maps`. `/maps` and `/stuck` are here
  (they can only describe what this world actually runs); `/tp` is not, because the reference
  teleports by asking the auth service for a world and having the client reconnect, and this world
  cannot start a travel on its own.
